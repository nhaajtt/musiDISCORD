Deploying musiDISCORD on a Raspberry Pi 5

S-01

What it runs on

One Pi 5 at home
no rented server

Hardware and software setup
ComponentDetails
BoardRaspberry Pi 5, 8 GB RAM, Kali Linux (aarch64), Raspberry Pi 6.12 kernel
Storage117 GB SD card. This is the weak spot: for long-term use, move to a USB SSD
ServicesDocker 28 and Compose 2.40, three containers: bot (Node.js 22), Lavalink v4, Uptime Kuma
Second screen3.5 inch 480×320 resistive touch TFT on the SPI bus, ILI9486 controller, plugged straight onto the 40-pin GPIO header
NetworkHome LAN; Tailscale for remote access without opening router ports
S-02

How the parts talk to each other

The bot gives orders
Lavalink handles the audio

Discord  <-->  bot (Node.js)  <-->  Lavalink  <--  music/ folder
                |
                +-- data/        SQLite and JSON (settings, stats, queues)
                +-- API :8787    bound to 127.0.0.1 only, token required
                |      +-- Tailscale serve  -->  phone, computer
                |      +-- display.py       -->  TFT screen (framebuffer, touch)
                +-- cron         backup at 4:30, self-update at 5:00

The bot does not play audio itself: it sends commands to Lavalink, which decodes the files in music/ and streams them into the voice channel. Splitting it this way keeps the bot light, while the heavy part lives on its own and restarts independently.

S-03

Deploying step by step

From a blank Pi
to a bot running 24/7

The fastest way: one command. The script installs Docker and git, asks for the bot token and application ID, generates the passwords, starts the bot and registers the slash commands. Optionally it also installs the backup and auto-update timers, and with --tft it sets up the 3.5-inch TFT screen too. It is safe to run again, and --dry-run only previews. It works on a Raspberry Pi or a Debian machine.

curl -fsSL https://raw.githubusercontent.com/nhaajtt/musiDISCORD/main/scripts/install-pi.sh | sh

To preview, add -s -- --dry-run after sh. The manual steps below are the hands-on way, for anyone who wants to control each part.

The manual way, step by step:

  1. SSH with a key, no passwords

    Generate a key on your main machine and copy it to the Pi. Note: if you set a passphrase, non-interactive mode will silently refuse it, so a key meant for automation should have no passphrase.

    ssh-keygen -t ed25519
ssh-copy-id nhaajt@<Pi address>

  2. Install Docker and set permissions

    Install Docker and Compose v2, then add your user to the docker group so you do not need sudo every time. Anything that needs root, I run separately.

    sudo apt install -y docker.io git
sudo usermod -aG docker $USER

  3. Get the code, music and config

    Clone the repo, then copy over the music/ folder and the .env file (it holds the token and is not in git). The Lavalink plugin is a Java file, so copy it straight from your main machine if the Maven server is unreachable.

    git clone https://github.com/nhaajtt/musiDISCORD.git

  4. Build and run

    One command builds all three containers. The bot only starts once Lavalink reports healthy, thanks to depends_on with a healthcheck.

    docker compose up -d --build

  5. Remote access with Tailscale

    Install Tailscale, enable the service at boot (a step I once forgot), then use serve to get a private HTTPS address for the status page and Kuma.

    sudo systemctl enable --now tailscaled
tailscale serve --bg --https=443 http://127.0.0.1:8787

  6. Schedules and the screen

    Add cron entries for backups and self-updates, plus an @reboot entry to bring up the TFT screen when the Pi starts.

S-04

Keeping it alive

Running is not enough
it has to recover on its own

Automated operations tasks
TaskHow it works
BackupsEvery day at 4:30. Uses VACUUM INTO to get a consistent SQLite copy even while the bot is writing, compresses it, keeps 14 copies, and can optionally push to the cloud with rclone.
Self-updateEvery day at 5:00: fetch the new commit, accept fast-forward only, rebuild, wait for the bot to be healthy; if it breaks, roll back to the previous version and report through Discord.
MonitoringUptime Kuma checks the bot and Lavalink and reports to a Discord channel through a webhook.
Remote accessTailscale with serve: an HTTPS address that only devices on my account can reach.
Easing SD card wearThe "still alive" heartbeat is written to RAM, periodic queue saving is turned off, and Docker logs rotate.
Several Lavalink nodesList them in LAVALINK_NODES (for example main=lavalink:2333,backup=lavalink2:2333) and start the second node with docker compose --profile ha up -d. When one node goes down, its players move to another. Every node must see the same music folder; /stats shows how many nodes are up.
ShardingOptional, SHARDS=auto or a number; all shards run in one process. One shard is enough up to 2,500 servers.
Auto restartDocker's restart policy, system services set to enable, and @reboot for the TFT screen.
S-05

A screen on the GPIO header

The hardest part of the project
the full story is in the devlog

The 3.5 inch resistive touch TFT shows what is playing: a large title, the artist, a progress bar, stylus-operated controls, and my avatar bleeding to the edge like a magazine cover. The display.py program reads the bot's status API and draws straight to the framebuffer, reading touch input through evdev.

What I learned most was how to break a hardware problem into testable hypotheses instead of trying things at random:

TFT screen experiments and results
What I triedWhat I sawTakeaway
Vendor overlay (tft35a, old fbtft driver)White screen, even when filling the framebuffer with a solid colorThe vendor only supports the Pi 3B and 4B
Official piscreen,drm overlay at 24 MHzBlack screenThe panel accepted the init commands but showed no pixels
Reading the SPI byte counterExactly 307,222 bytes added per frameThe Pi sends all the data, so suspect the speed
Lowering SPI to 8 MHzThe image appeared24 MHz is too high for this panel
Sending the full frame twice per secondAbout 614 KB per second, laggyThe 8 MHz bus handles roughly 1 MB per second
Sending only the changed regionChoppierMany small writes cost more than one big write
Redrawing once per second, no animationAbout 307 KB per second, smoothThe design has to follow the hardware limits
S-06

A status page for phones and big screens

The same data
two interfaces

The bot has a small status API and a /display page: a spinning disc that pulses to the track's real BPM (measured by the bot itself), a page color that changes with each song, and a ruler along the bottom made of beat ticks you can tap to seek. The page runs on a phone, tablet or big screen.

  • Only exposed on 127.0.0.1 on the machine running the bot; reached from outside through Tailscale.
  • Controls need DISPLAY_TOKEN; without a token you can only view.
  • No Discord IDs or requester names are exposed; the page hides itself during a music quiz.
  • A strict CSP: no inline scripts, no external resources.
